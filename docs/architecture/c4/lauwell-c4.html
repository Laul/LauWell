Level 1 · System context

One person, one app, and what it leans on

LauWell reads sensor data from Health Connect, signs the user in with Google through Firebase, and keeps what the user enters in Room, synced to Postgres on Neon. The rest of M9 moves raw readings there too and removes Firestore, now only read once to copy old Mood entries. Everything on the care side (medication, ostomy, labs) is still dashed.

Level 2 · Containers

One app, local stores, and a cloud side that is changing

Today sensor data stays on the phone (Health Connect holds the detail, Room caches daily summaries) and what the user enters is written to Room and synced to Postgres (Firestore only until old Mood entries are copied). The decision of 2026-11-04 set this: Room stays as the fast offline copy, a small sync API checks the Firebase ID token and writes to Postgres on Neon, and Postgres becomes the single source of truth for every entry and raw reading. Firebase Auth and Cloud Storage stay; Firestore is removed in M9.

  • Room is disposable today: a schema change drops it and the next sync rebuilds it from Health Connect. Once it also holds entries waiting in the outbox (M9), dropping it would lose unsynced writes, so migrations will need care.
  • Firestore writes return at once from its local cache and sync when online, so logging never waits on the network. The Room outbox and a WorkManager job rebuild that offline behaviour for Postgres.
  • The sign-in has two hops: Google hands the app an ID token, then Firebase Auth turns it into a session with a uid. The rules check that uid today; the planned sync API checks the same ID token and maps it to our own users.id. Neon's own sign-in is not used.
Level 3 · Components of the app

How a value gets onto a screen

There are two paths in and one path out. Sensor days flow Health Connect, Room, screens. The user's entries are written to Room and queued for Postgres, and screens read them from Room. Screens read both through one place, DailySummarySource, and never know which.

  • Syncs start from four triggers: each foreground, a 20-minute WorkManager job, a screen resuming, and the detail screen every minute. Background runs need the Health Connect background permission and a signed-in session.
  • Scrolling a chart back past the 91-day window loads older chunks from Health Connect into Room through DayHistory.
  • Built (M9): a Room outbox and a WorkManager job (EntrySync) send entries to Postgres through the sync API and pull changes for a second device; Mood is the first metric on it. Planned: the raw-readings table goes the same way. The daily-summary upload to Firestore is dropped.

Level 3 · Components of the Firebase project

What stays in Firebase and what goes

Firebase Auth and Cloud Storage stay. Firestore, its rules and the emulator tests are removed in M9. Until then everything sits under users/{uid}/ and only that uid can touch it; one record type exists today, the measurement, and the rules do not check the shape of a document.

Level 3 · Components of the Postgres store

Every entry and raw reading in one database we can query

Schema v1 runs on Neon (users, entries, file metadata, row-level security), and the sync API is deployed and called by the app; readings, backup and the phone side are still planned (milestone M9). The phone talks to the sync API, never to the database directly: the API checks the Firebase ID token, maps it to our own users.id, and upserts entries (readings later), and row-level security keeps every row scoped to that user. Postgres stays plain, so a dump and restore moves it to any host.

  • Rows reference users.id, never the Firebase uid, so a later change of sign-in provider touches only auth_identities.
  • Raw readings are upserted on the Health Connect record_id, so repeats create no duplicates. AI analysis reads derived values computed from them, which can be recomputed when a better idea comes.
  • Neon's free plan keeps six hours of history, so a nightly pg_dump to Cloud Storage with a tested restore is part of the plan. The sync API runs as a Firebase Cloud Function in us-east5 (Columbus, Ohio), next to Firebase Auth and near the database. Still open: which AI service may see health data.
  • Data is stored in AWS US East 2 (Ohio): Neon has no Canadian region, and storing it in the US was accepted on 2026-11-04.
Reading the diagrams against the vision

Where the picture and the plan differ

The app monitors, it does not yet manage care

Medication and ostomy are the two P1 features in the project brief, and both sit behind the Care tab placeholder. Level 1 shows the whole care side dashed.

The toggle rule has no switch

isVisible is used everywhere, but the repository behind it always returns everything on. The Settings toggles row is not started.

One record shape, in a store being replaced

Decisions list seven storage shapes. Only Measurement is implemented, in Firestore. The other six arrive with their first metric, as Postgres tables.

Cloud Storage is not in the app

Photos are planned for ostomy, but there is no Storage dependency and no Storage rules yet. In the plan it also holds the nightly database dumps.

Two Notion pages are out of date

Backend Approach (4 Oct) still describes Firestore as the store, but the decisions of 2026-11-04 replace it with Postgres on Neon. Modular Architecture (July) describes feature packages like vitals and activity; the code uses today, tracker, log, settings, onboarding, care and records.

Security moves to row-level security

The Firestore rules check ownership only. The Postgres version (row-level security plus the sync API's token check) is planned with its own tests. Ownership-only is fine for one user, and worth revisiting before exports or sharing exist.

CLAUDE.md still says Firestore

The code still uses Firestore until the Mood migration lands, so CLAUDE.md describes it. A Planning task under M9 updates CLAUDE.md and the docs afterwards.
